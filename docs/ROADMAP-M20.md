# 《星落远征》M16–M20 开发计划

> **状态**：正式开发规划草案（未开始实施）  
> **制定日期**：2026-10-11  
> **基线**：`fallen-star-0.15.0-alpha.2-source.zip` / `0.15.0-alpha.2` / `alpha2.html`  
> **范围**：自动化平衡、游戏原生 HUD/菜单、45 种物品的独立 3D 外观、人物与场景的完整交互动作、内容与性能整合。  
> **目标**：玩法/表现并行开发，保留现有确定性世界、旧版本存录和可继续扩展的 TypeScript + Three.js 技术栈。

## 0. 决策摘要

1. **数值和难度验收主要由无渲染的模拟器承担**。不同技能代理、策略、职业与种子交叉测试；人工验收只负责易用性、美术品质、动作可读性和趣味性，不再作为反复调数值的主要手段。
2. **正式玩家 UI 必须呈现在游戏画面内**。Three.js 世界视图 + 正交 2D UI 视图共同绘制到游戏画布；Vue/HTML 仅保留页面入口、加载失败、开发诊断以及必要的无障碍/输入法桥接，不再承担主要可见背包、装备、商店和图鉴。
3. **45 个现有物品定义全部须具有各自明确的 3D 造型方案与可追溯资产**，以相同资产家族支撑地面展示、背包图像、商店、拾取动画及人物装备；不能以所有剑共用同一外形、全部药水仅换颜色来宣称完成。允许用共享构件和程序生成配方产生*逐款独立且可辨识*的最终网格。
4. **物品在各场景的可见身份一致**；尚未鉴定的药水、卷轴、法杖、饰品必须由“本局随机外观身份”选取模型，而非依据隐藏真实 `definition` 选择，避免视觉泄露。
5. **拾取、开/关门、拉杆、开箱、饮用、阅读、施杖、投掷、装备等采用明确的动作语义与接触阶段**，不能复用 180ms 的 `idle` 作为正式交互；规则立即原子提交，表现读取成功动作收据，动画不决定命中、奖励或世界推进。
6. **先打通一条纵向流程，再批量扩展**：先完成 8–12 种跨类别资产、装备/背包与四种互动动作的真实链路，再拓展到 45/45；避免先制作大量无法进入游戏的孤立模型。

**重要约束**：当前规则标识 `alpha2-1` / commands 6，存储键 `dungeon-descent.m15`。纯 UI/美术改动不应修改其历史机械语义；确需增加机械动作/装备容量/存档字段时，另开新规则身份（建议 `alpha3-1`，命令协议与存档标识单独升级），旧版入口可恢复但不得静默修改旧摘要。

### 明确不做

- 不以全 3D 世界物体承载所有 UI 文本；2D HUD 可以渲染在同一游戏画布内。
- 不把原版 WazHack 的素材、模型、UI 贴图、文本或特定数值复制进项目。
- 不把“装备视觉栏”误认为必须新增规则装备槽；当前五槽位（头、胸、腿、主手、副手）+ 护符槽先完整可视化，未来扩槽另立规则变更。
- 不重构已确认可用的确定性模拟为实时帧驱动。
- 不新增主动跳跃，也不生成要求跳跃才能通过的关卡。

## 3. M16A：无渲染自动化平衡实验台

### 3.1 原则

使用 `GameSession`/纯模拟的公开视图与正式语义命令，不允许自动玩家修改世界内部状态、直接读取隐藏物品真实定义、增加免费回合、直接传送或注入测试补给。受控边界测试可以白盒构造状态，但不可与自然跑局混为一谈。

### 3.2 代理类型

- `novice`：只使用当前可见信息，保守治疗，不主动寻找隐含最优解，模拟新手常见错误；不得读取未鉴定信息。
- `survivor`：搜索补给、评估防具，主动撤退，维护生命/食物安全阈值。
- `fighter`：根据武器伤害与速度选择战斗，有限使用消耗品。
- `experimenter`：尝试鉴定、投掷、解咒、法杖和环境反制，承担受控探索风险。
- `oracle`：仅作为**离线理论上界**，允许额外内部信息时必须醒目标记，不纳入公平性或常规通关率。

### 3.3 实验设计

- **PR 冒烟**：3 起始配装 × 3 公开信息代理 × 10 种子 = 90 局；只作严重回归预警，不宣称难度统计成立。
- **夜间基线**：3 配装 × 3 代理 × 100 种子 = 900 局，输出种子配对差异。
- **里程碑分析**：3 配装 × 3 代理 × 1000 种子 = 9000 局；另跑武器/物品反事实实验和异常种子。
- 使用可配置 CPU 并发、总行动/时钟上限、卡住检测；高负载分批执行，记录完整配置和版本，不规定未经实测的绝对运行时间。
- 所有参数扫描使用**相同种子列表的配对对照**，并保留种子分层；输出 Wilson 胜率区间、层间死亡危险率、行动数分位数和 bootstrap 差异区间。

### 3.4 指标和诊断

游戏结束原因、每层死亡概率与原因、行动数/游戏 tick、职业胜率、治疗/食物消耗、怪物击杀、道具发现与使用、未知物品试用比例、负面状态发生/反制、伤害来源、商店金额、装备变更次数、稀有物资占比、每个关键种子的最短失败轨迹。

不能只把总体胜率设成硬性目标。先冻结 M15 的基线，之后由设计目标确定可接受区间。自动代理策略自身升级要单独版本化；不允许在不同策略版本间直接声称难度变好/变坏。

### 3.5 交付与门禁

新增 `src/balance/`、`scripts/balance-run.mjs`、`scripts/balance-report.mjs`、`tests/balance/`、`reports/balance/`；命令建议 `npm run balance:smoke`、`balance:nightly`、`balance:milestone`。检查同种子同代理完全复现、变更随机序列受到版本约束、人工可从失败报告一键重放。性能不得用浏览器平均 FPS 代替模拟吞吐；二者独立报告。

## 4. M16B/M19：游戏原生 UI 架构

### 4.1 分层

```text
GameSession / PublicView (只读公开状态)
            ↓
PresentationViewModel（UI 需要的排序、提示、显示身份）
            ↓
CanvasInputRouter —— Hover/Focus/Drag/Touch/Gamepad
            ↓
┌────────────────── 统一游戏画布 ──────────────────┐
│ WorldCamera (Three.js)：人物、装备、掉落、场景 │
│ UICamera (orthographic)：HUD、装备栏、背包、菜单 │
│ Tooltip/Selection/Target：画布内层、鼠标/触屏 │
└──────────────────────────────────────────────┘
            ↓
用户确认操作 → 语义命令 → GameSession.submit
```

- UI 所需状态可缓存，但不持有机械真值；排序、筛选、网格占位、模型缩略图均为呈现派生。
- 全部可视面板同画布渲染，不把 Vue `<dialog>` 当作正式游戏内 UI。
- 画布文字建议字形图集 / SDF 或位图字库，保证简繁中文和英文清晰；高 DPI 下字体不应受低分辨率场景像素化后处理影响。
- 触屏采用安全区、较大点按目标、长按说明、点击移动/拖放替代；可配置快捷栏，游戏暂停逻辑仍遵循已批准语义。
- Vue 保留启动器、开发诊断、无障碍镜像、文件上传下载桥和缺失 WebGL 兜底。无障碍镜像不可成为另一个独立的机械状态入口。

### 4.2 普通探索 HUD

- 左上：生命、法力、饱食、状态异常；可折叠成图标。
- 屏幕中央：人物、怪物、设施交互点、敌人预警；世界空间提示跟随实体，远处不显示隐藏信息。
- 底部：6–8 个快捷格，显示武器、药水、法杖、食物与交互键；快捷栏指向实例 ID，**不额外增加物品所有权或背包容量**。
- 右上可选小地图、深度、时钟；底部窄日志/即时战斗反馈可自动淡出。
- 默认完整地牢可视面积尽量大，战斗时不弹出阻断大面板。

### 4.3 装备页与背包（强制设计）

**角色装备页**：中央为装备当前实际物品的可旋转 3D 人物预览，周围按身体部位布置六个视觉槽位：头、胸、腿、主手、副手、护符。护符目前是规则专有 `charm`，视觉页需要列出，但无需强行显示在世界角色上；可选胸前挂件。显示装备攻击、防御、抗性、耐久、强化、已知诅咒和替换差值；未知信息不得泄露。拖放可操作，但**只有 `submit` 成功才更新机械装备状态**。

**背包**：保持已实现的 16 个物品实例容量，在 UI 中采用 4×4 可选网格（后期按重量/尺寸调整另立机械规格）；格中是从**实际 3D 模型离屏渲染/缓存**的高辨识缩略图，叠加数量、充能、耐久、诅咒/未鉴定标志。优先支持分类筛选、名称排序、两级选中、悬停细节、右键/长按操作菜单、同一实例的拾取/丢弃/穿戴/投掷/鉴定/应用操作。

**正式 UI 提供**：地图内近物选择、物品比较、目标选择、商店双列买卖、图鉴/笔记、日志、存读和选项菜单；全部呈现于游戏画布，支持键鼠与触屏，无须借用开发用侧栏。

### 4.4 布局与尺寸验收

- 桌面 16:9 和 16:10；手机 390×844 竖屏和 844×390 横屏；用浏览器模拟覆盖布局、真实设备单列实测补充。
- Canvas UI 元件必须有热区、焦点、禁用、长按提示状态；动画忙、回放、失焦和遮挡面板必须阻断非授权机械命令。
- 主要流程：开局→装备页→探索→拾取→背包使用→商店→目标选择→图鉴→存档→恢复，无 HTML 模态可见；文件选择器/辅助 DOM 可以保留。

## 5. M16C/M17B/M18B：逐物品 3D 资产管线

### 5.1 资产合同

对 `src/content/alpha2.ts` **全部 45 个 `ItemDef.id`** 建立一对一的完整资产登记，至少包含：

```ts
interface ItemVisualSpec {
  id: string;                   // 稳定 asset id，不是秘密物品真实定义的公开保证
  source: { kind:'glb'|'recipe'; uri:string; license:string; sha256:string };
  family: 'potion'|'scroll'|'wand'|'weapon'|'armor'|'accessory'|'food'|'tool';
  ground: { scale:number; rotation:[number,number,number]; anchor:[number,number,number] };
  preview: { cameraPreset:string; framing:number; background:'transparent' };
  hand?: { socket:string; gripPreset:string };
  worn?: { slot:string; meshGroup:string; maskRegions:string[] };
  lod?: string[];
  silhouetteTag: string;        // 设计验收：不得只是相同原型换色
}
```

> 以上为下一阶段新接口提案，不表示源码已有 `ItemVisualSpec`。

建议目录：

```text
src/visual/items/catalog.ts
src/visual/items/registry.ts
src/visual/items/appearance-resolver.ts
src/visual/items/presenter.ts
src/visual/items/thumbnail-cache.ts
assets-src/items/<item-id>.blend OR <item-id>.recipe.json
public/assets/items/<asset-id>.glb
scripts/build-item-models.mjs
scripts/audit-item-models.mjs
tests/visual/item-catalog.test.ts
```

所有可见形态复用同一资产的 mesh/material 描述：`groundMesh` 与 `previewRender` 选同一 `assetId`，人物装备则读取同一模型的握点或穿戴部件。缩略图可以缓存渲染结果，但不能引入另一套随意绘制的图标导致样貌不一致。

### 5.2 未鉴定物品的外观信息防线（强制）

当前 M15 会把药水、卷轴、法杖、饰品的真实 `definition` 在鉴定前隐藏，但会给出按种子洗牌的 `appearance` 数字。以后也要保持：

- `definition` 是规则身份，**未知时不向展示层泄露**。
- `appearanceKey = category + ':' + randomizedAppearance` 是当前局的可见模型身份；同局同类外观在背包、地面、商店、拾取动画中完全一致。
- 鉴定之后可显示真名、效果、档案图鉴，但原则上**同一实例的模型外观不应突然变成另一瓶/另一杖**；如要显示附加装饰，仅可增加已知标签或非机械视觉特效。
- 游戏重开后，同一个真实药剂效果可能对应不同瓶型；若每个真实效果固定一把独特造型，经验玩家会直接通过外形识别而破坏鉴定玩法。
- 对可直接认出的装备、工具和食物使用固定每定义模型；未知组则保证每个定义有足够数量的一一可分配外观配方/资产，但某个真实效果与某款外观的映射跨局重新随机。
- 不允许通过模型文件名、HTML `data-*`、工具提示、地图地面类别标识、alt 文本、缓存键与性能指标把隐藏身份输出给玩家可观察的接口；需要专门编写信息泄露测试。

### 5.3 美术生产方法

**优先程序化模块配方 + Blender 离线校正 + glTF/GLB 输出**，沿用 M15 的低模块面和克制像素贴图。可以共享瓶口、护手、刀鞘、皮带、金属扣、布卷、宝石等基础几何件，但每件最终资产都必须有独立的**体积、轮廓/饰件、可读材质特征**，不可只通过 RGB 区分。

每件物品需提供：`源配方/Blend`、`GLB`、`地面截图`、`背包缩略图`、`角色装备截图（若可装备）`、`许可证/原创声明`、`尺寸/朝向/枢轴/缩略图框选元数据`。视觉件存于 Git 或 LFS 的策略需另行评估；制作大图和未压缩源文件可放外部素材库，但必须在 manifest 中可追溯。

**首批纵向验证选取**：`sword`、`knife`、`maul`、`shield`、`helm`、`renewal`（未知瓶型）、`insight`（未知卷轴）、`cinder`（未知法杖）、`ration`、`lantern`、`emberRing`、`kit`（12 项）。涵盖主手/副手/头部/消耗品/工具/饰品及秘密身份。

### 5.4 45 件物品的逐件视觉任务清单

## 6. M18A：角色与机关的完整交互动作

### 6.1 动作语义表

| 语义 | 必须可见的动作段 | 环境/道具反馈 | 目标与接触 |
|---|---|---|---|
| `pickupLow` | 接近/转身 → 屈膝伸手 → 抓取 → 起身收纳 | 地面物体在抓取时转到手部/背包，不能瞬间消失 | 手掌对齐地面物体锚点 |
| `pickupHigh` | 抬臂 → 拿取 → 收纳 | 高架和挂钩物可独立演出 | 手指/掌心目标 |
| `doorPush` | 接近门扇 → 手扶门 → 用身体推门 → 放手 | 门围绕铰链开启，不是瞬间隐藏 | 掌心贴门把/门边 |
| `doorPull` | 抓门把 → 后撤牵引 → 松手 | 门随动作向角色拉开，动作与 `doorPush` 不混用 | 角色朝向与门铰链决定变体 |
| `leverPull` | 握把 → 下压/拉动 → 复位 | 杠杆转动、门锁/机关亮起或移动 | 握点和杠杆空间枢轴 |
| `chestOpen` | 靠近 → 俯身 → 扣锁 → 掀盖 | 箱盖打开，战利品随后出现 | 手掌/箱盖铰链 |
| `drink` | 取瓶 → 抬头倾瓶 → 放回/弃瓶 | 口部对齐、液体视觉反馈可选 | 手—口部接触 |
| `read` | 展开卷轴 → 阅读 → 消耗/收起 | 卷轴在手中展开、随后消失/收纳 | 双手/视线 |
| `zap` | 取杖 → 举杖指向 → 发射 → 回收 | 弹道从杖首，而非角色身体中心出发 | 右手握点/杖首 muzzle |
| `throw` | 后摆 → 出手 → 物体飞行 → 回稳 | 飞行物沿既定结果轨迹表现 | 掌心释放点 |
| `equip/unequip` | 腰/背部取用、披挂、握持切换 | 物体从收纳点移至装备挂点 | 模型 sockets 与遮罩 |

第一批必须完成 `pickupLow`、`doorPush`、`doorPull`/方向适配、`leverPull`、`chestOpen`；随后补充 drink/read/zap/throw/equip，并为不同武器增加基础专属战斗动作。

### 6.2 动作协议：不能让动画产生机械结果

```ts
interface PresentationActionReceipt {
  actionId: string;             // 对应已接受的一次正式命令
  command: string;              // 公开语义；不得泄露隐藏效果
  actorId: number;
  targetId?: number;
  motion: 'pickupLow'|'pickupHigh'|'doorPush'|'doorPull'|'leverPull'
        | 'chestOpen'|'drink'|'read'|'zap'|'throw'|'equip'|'unequip';
  logicalTicks: number;         // 规则已决定的花费
  start: { floor:number; x:number };
  end: { floor:number; x:number };
  cues: { kind:'reach'|'contact'|'release'|'recover'; phase:number }[];
}
```

它可以由已接受命令及其 `before/after` 公共状态、现有语义事件推导；若现有公开视图不足以还原目标与演出意图，再通过**明确版本化的只读表现收据**补充。模型文件、动画名称、渲染相位、UI 光标位置不进入机械随机或战斗判定。

对于 `submit` 已成功的动作：机械规则**先原子提交**，动画播放期间将 before→after 的可见变更按阶段插值。比如开门的规则通行状态已经更新，画面中的门扇在“手碰把手”相位才开始张开。失焦、切语言、读档、回放、低 FPS、WebGL 恢复时，表现必须直接落到稳定的 after 画面，绝不重复消耗时间/道具或发奖励。不能用“播放结束”的事件补交游戏命令。

**未被接受的命令**不得播放成功拾取/开门/拉杆动作；如有提示性受阻/推门失败动作，它必须是纯表现，不能触发规则副作用。

### 6.3 接触质量与动作制作

- 扩展现有项目 23 骨架，复用肩、肘、手腕、胸腰、脚步的姿势系统；需要时配置双手 IK、目标空间约束及角色对目标的微量视觉偏移，但不改逻辑坐标。
- 每种设施设置 socket：门把手、门铰、杠杆头、箱盖、拾取点、锅把等。空间锚点位于设施视觉配置，而不是由 UI 猜测。
- 动作分为 approach（预备）、reach（伸手）、contact（接触）、effect（反馈）、recover（回稳）。允许同一种动作适配不同高度与朝向，不要求每个物品自制整段动画；但**动作必须匹配物体类别且在关键帧有物理接触感**。
- 可先基于现有动作素材重定向与手工补帧，再使用 Blender 制作明确的互动 clip；资产来源/许可证进入 `SOURCES.md`。仅靠把整个身体往下平移 5cm 不能通过拾取验收。
- 角色移动仍由规则位置决定；动画可调整纯渲染根节点和手脚姿态，但不能让玩家穿墙、免费接近或绕过敌人。
- 第三人/实体特定动画允许视觉 LOD，低配设备可减少手指细节，但不可删除接触与设施状态反馈。

### 6.4 动作验收矩阵

每类动作至少测试：正向、反向、障碍拒绝、对象被消耗、暂停/失焦、存读/回放、低帧、连续按键、装备变化/手里已持物、同一目标不同场景。拾取录制必须能看到手先碰物、物体再收纳；拉杆必须看到握持—拉动—机关响应；门扇必须有开闭过程，不能只修改一帧的 `visible`。所有动作使用相同命令历史得出完全相同机械摘要。

## 7. M17A/M20：数值调参与性能验收

### 7.1 数值不是通关率单点优化

采用“配对种子 + 多策略 + 分层报告”方式，观察不同职业/武器相对强弱、意外死亡、资源稀缺、特殊能力反制机会、策略多样性；制定相对当前基线的控制范围。新增内容必须先做固定种子对照，再扩展到大量种子，异常仅在正式规则路径可复现时确认为真实问题。

统计必选：胜率与置信区间、最低 HP 分布、治疗效率/食物压力、怪物出伤占比、不同深度死亡风险、装备选用率、未鉴定试用后果、模拟死循环/无法抵达目标比例。模型 UI 改造期间跑独立的机械摘要回归，确保仅视觉变化不会改变难度曲线。

### 7.2 视觉与设备预算（目标，不是假定达标）

- 按单模型三档 LOD/简化、材质复用、网格批量化、场景远距离剔除，避免 45 种物品引发 45 份重复纹理与 45 个常驻预览场景。
- UI 缩略图优先**离屏批量渲染缓存纹理**，仅物品外观/强化可视状态变化时失效；绝不能每帧都重绘所有格子的独立 3D 场景。
- 模型制作阶段记录顶点/三角面、尺寸、纹理预算、可见最小像素、实际绘制调用；生产发布以选定真实目标手机 + PC 的中位/P95帧间隔和显存等实测设预算，不提前伪称兼容所有设备。
- 主场景以 60 FPS 为桌面体验目标；移动端初期可先以稳定 30 FPS 为最低体验门槛，最终阈值依实机基线和产品需求冻结；帧表现绝不改变规则 tick。
- 设备检查：WebGL context lost/recovered、模型异步加载竞态、切换装备后的 GPU 资源释放、关闭菜单后预览纹理回收、中文字体占用和横竖屏文字裁切。
